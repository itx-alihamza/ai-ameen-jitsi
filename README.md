# Self-hosted Jitsi Meet for Ameen

The video-conferencing host for Ameen meetings. Runs as its own Docker Compose
stack, separate from the Ameen frontend and backend containers.

This replaced Google Meet. 8x8 JaaS was never used — see
[Why self-hosted](#why-self-hosted).

---

## Where this lives, and why it moved

This stack is the top-level `ai-ameen-jitsi/` folder, a sibling of
`ai-ameen-frontend/`, `ai-ameen-migrated-backend/`, and `ai-ameen-database/`.

It **used to be** `ai-ameen-migrated-backend/infra/jitsi/`. It moved out because
it is not backend infrastructure: it is a separately deployed system with its
own lifecycle, its own upgrade cadence, its own secrets, and — in production —
potentially its own host. Living inside the backend repository implied a
coupling that does not exist. The backend never calls Jitsi; it signs a join
token and the *browser* connects.

**The compose project name is pinned to `jitsi`** in `docker-compose.yml`.
Compose otherwise derives the project name from the directory, so the rename
would have re-prefixed every container and named volume
(`jitsi_jitsi-prosody-config` → `ai-ameen-jitsi_jitsi-prosody-config`) — which
presents as "all the volumes vanished": Prosody re-registers its components from
scratch and the generated web configuration and certificates are rebuilt.
Pinning the historical name makes the move a no-op for a running deployment.

This folder owns everything it needs:

```text
ai-ameen-jitsi/
├── docker-compose.yml        # web · prosody · jicofo · jvb, pinned to stable-9955
├── .env.example              # copy to .env; every password in it is real
├── .gitignore                # ignores .env and certs/
├── generate-secrets.sh       # JWT_APP_SECRET + internal component passwords
├── generate-local-cert.sh    # local TLS cert whose SANs actually cover localhost
├── setup-local.sh            # one-command local bring-up
├── backup.sh                 # configuration only — this stack holds no user data
├── README.md
└── certs/                    # IGNORED. Local runtime only.
```

`certs/` is gitignored and `cert.key` is never committed, never copied into an
image, and never placed in a deployment transfer archive. Local certificates are
regenerated by `./generate-local-cert.sh`; **Ubuntu production must use a valid
certificate for the real domain**, obtained through this stack's Let's Encrypt
flow (`ENABLE_LETSENCRYPT=1`) — see [VPS deployment](#vps-deployment).

The orchestration that brings this stack up alongside the application, locally
and on Ubuntu, is in [`../deployment/`](../deployment/).

## What this is

Four containers — `web`, `prosody`, `jicofo`, `jvb` — that together serve a Jitsi
Meet deployment at a domain you control. Ameen's backend generates an unguessable
room name per virtual meeting, and issues a short-lived per-user token that this
deployment verifies before admitting anyone.

Ameen's frontend embeds the conference in the meeting workspace's **Live Meeting**
tab using Jitsi's `external_api.js`, loaded from this host.

**Scripts in this directory**

| Script | Purpose |
|---|---|
| `setup-local.sh` | One command to get a working local stack: localhost `.env`, secrets, certificate |
| `generate-secrets.sh` | Generates/rotates the four credentials (`--force` to rotate) |
| `generate-local-cert.sh` | TLS certificate with SANs covering `localhost`, `127.0.0.1`, and the LAN IP; prefers mkcert |
| `backup.sh` | Backs up configuration volumes and `.env` (contains a secret — store encrypted) |

---

## Why self-hosted

Both alternatives put the media path *and the room's access policy* inside a
third-party account:

| | Google Meet | 8x8 JaaS | Self-hosted Jitsi |
|---|---|---|---|
| Who can admit a participant | Google, per Google's rules | 8x8, per the tenant's JaaS config | Ameen, per Ameen's RBAC |
| Where audio/video travels | Google's infrastructure | 8x8's infrastructure | Infrastructure the operator controls |
| Room creation coupled to | A Google Calendar event | A JaaS tenant and API key | Nothing — Ameen allocates a name |
| Data-residency control | None | None | Whatever the VPS provides |

For confidential board minutes belonging to Saudi organizations, the first column
is the deciding one. Ameen is the authorization boundary for every other resource
in the product; a conference room that a vendor console could admit someone to
would be the one exception, and it would be the exception on the most sensitive
surface.

There is a second, practical reason. Google Meet conference creation was
inseparable from writing a Google Calendar event (`conferenceData.createRequest`),
so a meeting could not have a video room unless its organizer had personally
connected Google. Now Ameen owns the room, and Google Calendar is genuinely
optional: a meeting with no Google connection is fully functional and simply is
not mirrored to an external calendar.

## What is deliberately absent

These are not oversights or "to do later" items. Each is a service that would have
to be *added* for the capability to exist:

| Absent | Would enable | Why it is out of scope |
|---|---|---|
| `jibri` | Recording, live streaming | Ameen stores no audio or video. No recording service, no media volume, no media bucket. |
| `jigasi` | SIP dial-in, transcription bridge | **Planned, not yet added** — see "Live transcription" below. Adding it is the next step for transcription, and it narrows a privacy guarantee, so it is a deliberate decision rather than a default. |
| `etherpad` | Shared notes | Minutes live in Ameen under its RBAC and approval workflow, not in an unauthenticated pad. |

### Live transcription (Speechmatics) — audio path not yet built

The Ameen backend has a complete, tested **Speechmatics Realtime** client
(`src/modules/integrations/speechmatics/`). Nothing feeds it audio yet, so no
meeting is transcribed today.

**Why this stack cannot transcribe as configured:**

| Component | Status |
|---|---|
| `ENABLE_TRANSCRIPTIONS` on web / prosody / jicofo | `0` |
| `jigasi` service | not declared, not running |
| Jigasi↔Speechmatics adapter | does not exist |

**Jigasi has no Speechmatics backend.** Inspecting `jigasi.jar` in
`jitsi/jigasi:stable-9955` shows exactly four transcription services — Google Cloud,
Oracle, Vosk, and Whisper. So Jigasi cannot call Speechmatics directly, and the
integration needs an adapter in between:

```
Jitsi
  → jigasi                 (joins as a transcriber participant; one audio stream per participant)
  → Vosk-protocol WebSocket (raw PCM in, {"eof":1} to end)
  → Ameen adapter           ← NOT BUILT: speaks Vosk on one side, Speechmatics on the other
  → Speechmatics Realtime   ← BUILT and tested
  → Ameen backend           → realtime to browser, final segments to PostgreSQL
```

The seam is `org.jitsi.jigasi.transcription.vosk.websocket_url` — a configurable
endpoint, with `EOF_MESSAGE` and `generateWebsocketUrl` confirmed present in the
class. `jitsi/jigasi:stable-9955` publishes an `arm64` build, so it runs on Apple
Silicon alongside the rest of this stack.

**Two things to decide before adding Jigasi:**

1. **Jigasi delivers one audio stream per participant**, so speaker identity comes
   from the actual Jitsi participant — better than voice diarization, and it makes
   Speechmatics' `diarization: speaker` largely redundant per stream. Prefer
   participant identity in the mapping layer.
2. **It narrows a privacy guarantee this file currently makes.** Today the answer to
   "can anything server-side hear the room?" is "no such service exists". A
   transcriber participant has audio access. Recording stays disabled — no Jibri, no
   media volume, `DISABLE_LOCAL_RECORDING=true` — but the claim changes, and the
   wording above must change with it rather than quietly becoming untrue.

**Audio handling when it is built:** audio exists transiently in memory while being
streamed. It is never written to PostgreSQL, Supabase Storage, disk, a Docker
volume, a temporary file, or a log. It does transit Speechmatics' service, which
processes it under that account's terms — a new processor in the path for
confidential board audio, and likely a DPA question.

**Configuration** lives in the backend `.env`, not here: `SPEECHMATICS_API_KEY`
(empty in `.env.example`; never committed, logged, or returned by an API),
`SPEECHMATICS_REALTIME_URL`, `SPEECHMATICS_LANGUAGE` (`ar` or `en` — not
user-selectable), and the diarization/partials/delay settings. Verify with
`npm run verify:speechmatics` (opt-in, gated on `SPEECHMATICS_REAL_TEST=true`; prints
no key).

Recording is denied in three independent places, so no single change re-enables it:

1. No `jibri` service exists in `docker-compose.yml`.
2. `ENABLE_RECORDING=0`, `ENABLE_LIVESTREAMING=0`, `ENABLE_TRANSCRIPTIONS=0` on
   `web`, `prosody`, and `jicofo`.
3. The join token Ameen mints sets `context.features.recording = false`,
   `livestreaming = false`, `transcription = false` per user.

The Ameen frontend additionally omits the recording, streaming, and captions
buttons from its `TOOLBAR_BUTTONS` allow-list — but that is cosmetic, and is not
counted among the three.

> **On `jitsi-web-transcripts`.** The `web` image declares that path whether or not
> transcription is enabled. With `ENABLE_TRANSCRIPTIONS=0` and no `jigasi`,
> nothing ever writes to it. It is not a media store and holds no audio or video.

## Services

| Service | Role | Exposed | Notes |
|---|---|---|---|
| `web` | nginx + the Jitsi Meet app; serves `external_api.js` | 80, 443 | 80 exists only for the ACME challenge and the HTTPS redirect |
| `prosody` | XMPP signalling **and JWT verification** | internal only | The security-relevant service — see [Authentication](#authentication) |
| `jicofo` | Conference focus; allocates bridges, assigns roles | internal only | |
| `jvb` | Videobridge; carries the actual media | 10000/udp | The service with the unusual network requirement |

Media passes through `jvb`'s memory and is never written to disk. There is no
recording sink configured and no volume that could hold one.

Every service declares a health check that tests the *function* rather than the
process: nginx serving the app root, Prosody answering `prosodyctl status`, and
jicofo/jvb reporting `/about/health` — the last of which is true only once the
component has registered with Prosody and can accept a conference. `web` and the
two components wait on `prosody: service_healthy`, so a cold `up` does not produce
a window where the app loads but no conference can start.

All four use `restart: unless-stopped`: they recover from a crash and from a host
reboot, but a deliberate `docker compose stop` stays stopped.

## Local development

### Start to finish

1. **Start Docker Desktop** and wait for the engine to report running.
2. **Run the setup script** — writes a localhost `.env`, generates the four secrets,
   and generates a TLS certificate covering `localhost`:
   ```bash
   cd ai-ameen-jitsi
   ./setup-local.sh
   ./setup-local.sh --print-backend-env >> ../ai-ameen-migrated-backend/.env   # secret never printed
   ```
3. **Start Docker Compose**:
   ```bash
   docker compose up -d
   docker compose ps        # wait for all four to be (healthy)
   ```
4. **Open `https://localhost:8443`** in a browser.
5. **Accept the certificate warning** (or install mkcert first — see below). This is
   required once per browser *before* using the Live Meeting tab.
6. **Restart the backend** so it picks up the new environment — `tsx watch` reloads
   source but not `.env`:
   ```bash
   cd ../.. && npm run dev
   npm run verify:jitsi     # confirms the backend and Jitsi agree
   ```
7. **Start the frontend**:
   ```bash
   cd ../ai-ameen-frontend && npm run dev
   ```
8. **Open the Ameen application** at `http://localhost:3000`, sign in as
   `admin@demo-ameen.local` / `AmeenDev@2026!`, create a virtual meeting, and open its
   **Live Meeting** tab.


**One command:**

```bash
cd ai-ameen-jitsi
./setup-local.sh
```

That writes a localhost-tuned `.env`, generates the four secrets, and generates a
TLS certificate whose SANs cover `localhost`, `127.0.0.1`, `::1`, and your LAN
address. It prints the block to paste into the backend's `.env` — **without the
secret**, which you read from the file:

```bash
grep '^JWT_APP_SECRET=' .env
# or, without it ever appearing on screen:
./setup-local.sh --print-backend-env >> ../ai-ameen-migrated-backend/.env
```

Then:

```bash
docker compose up -d
docker compose ps          # wait for all four to report healthy
```

> **Restart the Ameen backend after changing its `.env`.** `tsx watch` reloads
> changed *source*, not the environment — `load-env` runs once at process start. A
> backend started before the `JITSI_*` variables were added reports
> `providerStatus: "not_configured"` and `tokenAuthentication: false`, which looks
> exactly like a broken integration. Confirm with `npm run verify:jitsi`.

Confirm the wiring end to end, from the backend directory:

```bash
npm run verify:jitsi
```

That audits room entropy, URL construction, and the exact JWT claim shape Prosody
requires — against the values actually in `.env`. It is the check that catches a
mismatched `JITSI_JWT_APP_SECRET`, the most common cause of "every join is rejected".

### Opening it in a browser

1. Visit **`https://localhost:8443`** directly, once.
2. Accept the certificate warning.
3. Only then open the Ameen Live Meeting tab.

Step 1 is not optional with a self-signed certificate. A browser will not load a
*subresource* (`external_api.js`) from an origin whose certificate it has not
accepted, and it shows no prompt when the request comes from a script — so the Live
Meeting tab would stay blank with no visible reason. Repeat once per browser and per
browser profile.

**To skip the warning entirely**, install mkcert first — `generate-local-cert.sh`
prefers it and produces a certificate your OS and browsers already trust:

```bash
brew install mkcert
./generate-local-cert.sh localhost
docker compose restart web
```

### Stopping and restarting

```bash
docker compose stop            # stop, keep configuration and certificates
docker compose start           # start again
docker compose restart web     # after replacing the certificate
docker compose down            # remove containers, keep volumes
docker compose down -v         # ALSO delete config volumes — forces a clean rebuild
```

### Troubleshooting camera and microphone locally

| Symptom | Cause | Fix |
|---|---|---|
| Live Meeting tab blank; console shows a failed `external_api.js` load | Certificate not accepted for `https://localhost:8443` | Visit that URL directly and accept the warning, or use mkcert |
| Mic/camera prompt never appears | The page is not a secure context | Both Ameen and Jitsi must be HTTPS. `localhost` counts as secure; a bare LAN IP does not without a trusted certificate |
| Prompt appeared once, then permission denied with no retry | The browser remembered the denial | Chrome: padlock → Site settings → reset permissions. Safari: Settings → Websites → Camera/Microphone |
| Call connects but a second device gets no audio or video | `DOCKER_HOST_ADDRESS` is `127.0.0.1` | Set it to the LAN address (`setup-local.sh` detects it), then `docker compose up -d` |
| A second device rejects the certificate | Its SANs do not cover the LAN IP | Re-run `./generate-local-cert.sh` on the host; it includes the detected LAN IP |
| `ERR_CERT_COMMON_NAME_INVALID` | The image's built-in fallback certificate is being served | `./generate-local-cert.sh`, then `docker compose restart web` |

### Two things that only a real stack revealed

**The browser needs `host:port`, the JWT needs the bare host.** The join response's
`domain` is what the frontend passes to `new JitsiMeetExternalAPI(domain, …)`, and the
IFrame API builds the `external_api.js` URL from it. With the bare hostname the
browser requested `https://localhost/external_api.js` — port 443 — and got
`ERR_CONNECTION_REFUSED` while Jitsi was healthy on 8443, so the tab showed a
connection error for a working deployment. `domain` now carries the port;
the JWT `sub` still carries the bare hostname, because Prosody compares `sub`
against its own domain and a port would never match.

**Browser-side local recording defaults to ON.** The image templates
`config.localRecording.disable` from `DISABLE_LOCAL_RECORDING`, which defaults to
`false`. Ameen's `configOverwrite` switched it off for the embedded frame, but a
moderator opening the room URL directly would have got the server default.
`docker-compose.yml` now sets `DISABLE_LOCAL_RECORDING=true`, verified in the running
container.

### A note on `JITSI_DOMAIN=localhost`

`localhost` is used deliberately: browsers treat it as a secure context, so
`getUserMedia` works with only a self-signed certificate to accept. For a named host
instead, add it to `/etc/hosts`, pass it to the cert script, and keep it consistent
in this `.env` and the backend's `JITSI_DOMAIN`/`JITSI_PUBLIC_URL`:

```bash
echo '127.0.0.1 meet.ameen.local' | sudo tee -a /etc/hosts
./generate-local-cert.sh meet.ameen.local
```

## VPS deployment

Two vCPU and 4 GB RAM comfortably handles a board meeting; the constraint is
network throughput, not CPU, until you reach dozens of simultaneous participants.

```bash
# 1. DNS: an A record for meet.example.sa → the VPS public IPv4 address.
#    Do this first and let it propagate — the ACME challenge in step 5 needs it.

# 2. Docker
curl -fsSL https://get.docker.com | sh

# 3. Configuration
git clone <this-repo> && cd ameen-nextjs/ai-ameen-jitsi
cp .env.example .env
./generate-secrets.sh

# 4. Edit .env
#      JITSI_DOMAIN=meet.example.sa
#      PUBLIC_URL=https://meet.example.sa
#      DOCKER_HOST_ADDRESS=<public IPv4>
#      ENABLE_LETSENCRYPT=1
#      LETSENCRYPT_EMAIL=ops@example.sa
#      LETSENCRYPT_USE_STAGING=1     ← while verifying; see below

# 5. Firewall (see the next section for why each port)
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 10000/udp
ufw enable

# 6. Start
docker compose up -d
docker compose ps
```

Verify with `LETSENCRYPT_USE_STAGING=1` first. The production ACME endpoint
rate-limits failed attempts per domain per week, and a DNS record that has not
propagated burns through that allowance quickly. Once a staging certificate
issues successfully, set it to `0` and:

```bash
docker compose down
docker volume rm jitsi_jitsi-web-config    # discard the staging certificate
docker compose up -d
```

Finally, set the Ameen backend's `JITSI_*` variables to the public domain and
restart it.

**If a VM sits behind NAT** (a private address on the interface, a separate public
address), advertise both so ICE can choose:

```ini
DOCKER_HOST_ADDRESS=<public-ip>
JVB_ADVERTISE_IPS=<public-ip>,<private-ip>
```

## Render and other PaaS hosts

**Do not treat Render's free tier as a production Jitsi host.** Render can be used
experimentally, but Jitsi's requirements conflict with what a typical PaaS
provides:

| Jitsi needs | Typical PaaS free tier |
|---|---|
| Persistent processes | Sleeps after idle; a sleeping videobridge drops every call |
| **Arbitrary UDP ports** | HTTP/TCP only — this alone is disqualifying |
| A stable public IP to advertise | Ephemeral, rotating addresses |
| WebRTC media throughput | Bandwidth-metered, optimized for request/response |
| Reliable uptime | Best-effort on free tiers |
| Predictable networking | Proxy layers that terminate and re-originate connections |
| Long-lived connections | Aggressive idle timeouts |

The UDP requirement is the decisive one. `jvb` exchanges media over UDP/10000; a
platform that forwards only HTTP traffic cannot carry it. Jitsi's TCP/443 fallback
exists for participants whose *own* network blocks UDP, not as a way to run the
bridge without it — routing every participant through TCP fallback degrades
quality badly and does not remove the need for a stable advertised address.

Use a plain VPS with a public IPv4 address, root access, and unmetered or
generously metered bandwidth.

## HTTPS is not optional

Browsers expose `getUserMedia` (microphone, camera) and `getDisplayMedia` (screen
sharing) **only in a secure context**. Over plain HTTP:

- microphone and camera requests fail, usually with no visible error;
- screen sharing is unavailable;
- WebRTC may negotiate and then carry no media, so the call *appears* to connect
  and everyone sits in silence;
- the browser refuses `external_api.js` as mixed content when the Ameen page is
  itself HTTPS, and the Live Meeting tab shows only a load failure.

These symptoms look like Jitsi bugs. They are the absence of TLS.

`DISABLE_HTTPS=1` exists for `http://localhost` development only — `localhost` is
treated as a secure context by browsers. Any other host, including a LAN IP
address, needs a real certificate.

The Ameen frontend must also be served over HTTPS: an HTTPS iframe inside an HTTP
page is blocked, and vice versa.

## Firewall and network requirements

| Port | Protocol | Direction | Purpose | Required |
|---|---|---|---|---|
| 443 | TCP | inbound | The app, BOSH signalling, `external_api.js`, TCP media fallback | Yes |
| 10000 | UDP | inbound | All WebRTC media | Yes |
| 80 | TCP | inbound | ACME HTTP-01 challenge, HTTPS redirect | Only with `ENABLE_LETSENCRYPT=1` |
| 22 | TCP | inbound | Administration | Restrict to known addresses |
| 5222, 5280, 5347 | TCP | — | Internal XMPP | **Never expose** |
| 8080 (jvb), 8888 (jicofo) | TCP | — | Health/REST endpoints | **Never expose** |

Only `443/tcp` and `10000/udp` need to be open for a working deployment. If
participants report connecting but hearing nothing, `10000/udp` is closed
somewhere — that is the single most common cause.

## Authentication

`ENABLE_AUTH=1` with `AUTH_TYPE=jwt` makes Prosody reject any join that does not
present a valid token. `ENABLE_GUESTS=0` is load-bearing: with guests enabled, an
unauthenticated browser can join a room whose name it knows and the token check
becomes advisory.

Ameen's backend mints each token with:

- `room` scoped to **one** room name — not the `*` wildcard many tutorials use.
  A wildcard token issued for one board meeting would open every other
  organization's room on the same host.
- `aud` and `iss` set to `JWT_APP_ID`, `sub` to the Jitsi domain.
- `exp` one hour out by default, so a token is not a standing credential.
- `context.user.moderator` mirroring Ameen's own meeting-control authority, so
  Jitsi moderator rights are a projection of Ameen RBAC rather than a parallel
  permission system.
- `context.features.recording / livestreaming / transcription` explicitly
  `false` — denied rather than omitted, because some Jitsi builds read an absent
  feature flag permissively.

`JWT_APP_SECRET` lives on this host and in the Ameen backend's environment. It is
never sent to a browser, never included in a frontend build, and never logged.

**If token authentication is not configured** (either `JWT_APP_ID` or
`JWT_APP_SECRET` unset), room security rests on unguessable names alone. Ameen
detects this and shows a warning in the Live Meeting tab rather than letting an
operator assume rooms are locked. Acceptable for local development; not for
confidential meetings.

## How Ameen authorizes a join

The room URL is never in the meeting payload. It is produced only by
`POST /api/meetings/:id/live/join`, and only after every one of these passes:

1. `ameen_token` cookie — the only accepted credential.
2. Email verification, re-checked against the database rather than the JWT claim
   (a token minted before verification was revoked still carries the old claim).
3. Organization membership.
4. The meeting belongs to the caller's organization — enforced by an
   `organization_id` filter **and** by PostgreSQL RLS beneath it.
5. Participant scope: attendee, board member, committee member, organizer, or a
   tenant-wide governance role (`Admin`, `Board Secretary`). `Auditor` is
   deliberately excluded — read-only has no business inside a live call.
6. Lifecycle state: an archived meeting's room is closed, and a room opens 30
   minutes before the scheduled start (or immediately once the meeting has
   actually been started).
7. `meetings.view` permission, at the route.
8. The attempt is written to `meeting_events` — allowed or denied.

Requests are rate-limited per user per meeting. A meeting in another organization
returns the same `404` as one that does not exist, so a caller probing ids learns
nothing.

Room names carry ~130 bits of entropy and are never derived from a meeting title
or id. That is defence in depth *behind* the checks above, not instead of them: a
forwarded link is still refused at the Ameen boundary, and — with token auth
configured — at the XMPP layer too.

## Secrets

```bash
./generate-secrets.sh              # fill only empty values
./generate-secrets.sh --force      # rotate everything
```

Generates with `openssl rand -hex`:

| Value | Length | Consequence if weak |
|---|---|---|
| `JWT_APP_SECRET` | 32 bytes | Anything holding it can mint a token for any room — full access to every meeting |
| `JICOFO_AUTH_PASSWORD` | 24 bytes | Anything reaching the internal network can register as the conference focus |
| `JVB_AUTH_PASSWORD` | 24 bytes | Same, for the media bridge |

`.env` is gitignored and `chmod 600`. Never commit a real value.

**Rotating the internal passwords requires clearing Prosody's volume**, which
still holds the old registrations:

```bash
docker compose down
docker volume rm jitsi_jitsi-prosody-config
docker compose up -d
```

Skipping that leaves jicofo and jvb unable to authenticate, which presents as
conferences that never connect.

Rotating `JWT_APP_SECRET` needs no volume change, but the Ameen backend's
`JITSI_JWT_APP_SECRET` must be updated in the same window — tokens minted with the
old secret are rejected immediately, so an in-progress call survives (the token was
already accepted) while new joins fail until both sides agree.

## Upgrades

```bash
# 1. Read the release notes for the target tag before moving it.
#    Jitsi occasionally changes configuration variable names between stable tags.

# 2. Pin the new tag
#      JITSI_IMAGE_TAG=stable-XXXXX

# 3. Back up first — see the next section
./backup.sh

# 4. Pull and recreate
docker compose pull
docker compose up -d

# 5. Verify
docker compose ps                        # all four healthy
#    Then open a real meeting from Ameen and confirm audio and video both work.
#    A conference that connects with no media is the characteristic symptom of a
#    variable that was renamed.
```

Because every customization is an environment variable or an Ameen-side
`configOverwrite`, no image is patched and `docker compose pull` is safe. Do not
edit files inside a container or bake a modified image: that is what makes
upgrades painful, and it is why the Ameen frontend uses only supported
configuration options.

**Roll back** by restoring the previous `JITSI_IMAGE_TAG` and running
`docker compose up -d`. Configuration volumes are generally forward-compatible
within a major line; across one, restore from backup.

## Backups

There is no user data here. Meetings, minutes, decisions, and attendance live in
Ameen's PostgreSQL; no audio or video exists anywhere in this stack. What is worth
backing up is *configuration*, so a rebuild does not mean re-issuing certificates
and re-registering components.

```bash
cat > backup.sh <<'SCRIPT'
#!/usr/bin/env bash
set -euo pipefail
STAMP="$(date +%Y%m%d-%H%M%S)"
DEST="${1:-./backups}/jitsi-$STAMP"
mkdir -p "$DEST"

# .env holds every secret, so the archive must be treated as a secret too.
cp .env "$DEST/env.backup"

for volume in web-config prosody-config prosody-plugins jicofo-config jvb-config; do
  docker run --rm \
    -v "jitsi_jitsi-$volume:/source:ro" \
    -v "$(cd "$DEST" && pwd):/backup" \
    alpine tar czf "/backup/$volume.tar.gz" -C /source .
done

chmod -R 600 "$DEST"
echo "Backup written to $DEST"
SCRIPT
chmod +x backup.sh
```

Restore:

```bash
docker compose down
docker run --rm -v jitsi_jitsi-prosody-config:/target \
  -v "$(pwd)/backups/jitsi-<stamp>:/backup:ro" \
  alpine sh -c 'rm -rf /target/* && tar xzf /backup/prosody-config.tar.gz -C /target'
docker compose up -d
```

Store backups encrypted and off-host: `env.backup` contains `JWT_APP_SECRET`.

**Operational requirements beyond backup:** monitor `443/tcp` and `10000/udp`
reachability (a firewall change that closes the UDP port produces silent calls,
not an error); watch certificate expiry if a proxy terminates TLS instead of the
built-in ACME client; and keep the host's clock synchronized — JWT `exp`/`nbf`
validation fails when the Jitsi host and the Ameen server disagree by more than a
few seconds.

## Local verification status

What has been verified on a developer machine, and what has not. Stated separately
because "the configuration is right" and "a call actually works" are different
claims.

| Verified | How |
|---|---|
| Compose composition | `docker compose config` — exactly `web`, `prosody`, `jicofo`, `jvb`; no jibri/jigasi/etherpad; every recording and transcription flag `0`; no audio, video, or recording volume |
| Certificate is browser-grade | A real TLS 1.3 handshake against `localhost` with full hostname verification, and a name outside the SANs correctly rejected |
| JWT contract | `npm run verify:jitsi` — 22 checks against the secret actually in `.env`: single-room scope (never `*`), `aud`/`iss`/`sub`, expiry, moderator projection, recording/streaming/transcription denied, secret absent from the returned grant, tampered and foreign-secret tokens rejected |
| Ameen authorization chain | 45 live HTTP checks against the running backend: unauthenticated 401, `Authorization: Bearer` rejected, room name never present in `live/state`, Auditor refused, cross-tenant 404 byte-identical to a nonexistent meeting, start/end idempotent, join rate-limited, audit rows written without the room name |
| Live Meeting UI | 49 real-browser checks (Puppeteer, `npm run verify:live-meeting` in the frontend) across desktop/laptop/tablet/mobile plus Arabic RTL: locked-tab affordances with accessible reasons, no horizontal overflow, no clipped text, transcription "Not configured", and the Jitsi connection-failure path |

| **Not** verified locally | Why |
|---|---|
| `docker compose up` with real containers | The Docker daemon in the development sandbox has no working registry egress: it transferred no layers of a 3 MB image in 50 s, while shell `curl` reached `registry-1.docker.io` in 0.3 s. The images could not be pulled, so the stack was never started. |
| A real conference — microphone, camera, screen share, participant list, lobby, moderator controls, multi-participant media | All require the running stack. Follow the manual steps in "Local development" once the images can be pulled. |
| Media over a real network path (`10000/udp`) | Same reason. This is the step most likely to need a `DOCKER_HOST_ADDRESS` correction, and the one that cannot be inferred from configuration. |

Everything in the first table is reproducible with the commands named in it.

## Troubleshooting

### The Live Meeting tab shows "Could not load the meeting client"

`external_api.js` did not load from this host.

```bash
curl -I https://meet.example.sa/external_api.js    # expect 200
docker compose ps web
docker compose logs --tail=50 web
```

Locally, this is almost always the untrusted self-signed certificate — visit the
Jitsi URL directly and accept the warning. In production, check that the Ameen
frontend is also HTTPS: an HTTP page cannot load an HTTPS script and vice versa.

### The call connects but nobody can hear anything

`10000/udp` is not reachable, or `DOCKER_HOST_ADDRESS` advertises an address
participants cannot route to. This is the single most common failure.

```bash
grep DOCKER_HOST_ADDRESS .env      # must be the LAN (dev) or public (prod) IP
docker compose logs jvb | grep -i 'harvest\|address'
nc -zvu meet.example.sa 10000      # from a participant's network
ufw status | grep 10000
```

Never `127.0.0.1` — that address means "this container" to the participant.

### Microphone or camera unavailable

Almost always a secure-context problem. Confirm the page is HTTPS with a
certificate the browser trusts. Then check the browser's own site permissions —
a previously denied prompt is remembered and will not be shown again.

### Every join is rejected

The token is not being accepted.

```bash
docker compose logs prosody | grep -i 'token\|auth'
```

Check, in order:

1. `JWT_APP_ID` here equals `JITSI_JWT_APP_ID` in the Ameen backend.
2. `JWT_APP_SECRET` here equals `JITSI_JWT_APP_SECRET` there — exactly, with no
   trailing whitespace or quotes.
3. Both hosts' clocks are synchronized (`timedatectl status`). A skew larger than
   the token's small tolerance fails `nbf`/`exp` validation.
4. The Ameen backend was restarted after its `.env` changed.

### Anonymous users can open a room

Token authentication is off or half-configured.

```bash
grep -E 'ENABLE_AUTH|ENABLE_GUESTS|AUTH_TYPE|JWT_APP' .env
```

`ENABLE_AUTH=1`, `ENABLE_GUESTS=0`, `AUTH_TYPE=jwt`, and **both** `JWT_APP_ID` and
`JWT_APP_SECRET` set. Ameen treats a half-configured pair as "no token auth" and
issues no token, so a partial configuration silently degrades to open rooms.
Recreate the stack after fixing it — Prosody reads these at startup.

### `jicofo` or `jvb` will not become healthy

Usually an internal password that no longer matches Prosody's stored registration
(see [Secrets](#secrets)).

```bash
docker compose logs jicofo | tail -50
docker compose logs prosody | grep -i 'authentication failed'
```

### Certificate issuance fails

```bash
docker compose logs web | grep -i 'letsencrypt\|acme'
dig +short meet.example.sa       # must return this server's public IP
curl -I http://meet.example.sa/.well-known/acme-challenge/test
```

Port 80 must be reachable from the internet and DNS must have propagated. Use
`LETSENCRYPT_USE_STAGING=1` while debugging so the production rate limit is not
consumed.

### Where the logs are

```bash
docker compose logs -f                # everything
docker compose logs -f jvb            # media problems
docker compose logs -f prosody        # authentication problems
docker compose logs -f web            # certificate and asset problems
docker compose logs -f jicofo         # conference allocation problems
```
